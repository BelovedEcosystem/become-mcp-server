# BECOME MCP Server — Repository & Design Audit (2026-09-10)

Scope: everything in this repository (`README.md`, `docs/CLAUDE-CONNECTOR.md`,
`skills/become-use/SKILL.md`, `.gitignore`, `LICENSE`, full git history) plus the
publicly documented design of the hosted service. The live host
(`mcp.belovedecosystem.com`) was **not reachable** from the audit environment
(egress proxy 403), so runtime behaviour (TLS, 401 handling, `/agent.md`
content, tool schemas) is **unverified**.

Severity scale: **High** = fix before wider distribution · **Medium** = fix soon ·
**Low** = hygiene / clarity.

---

## 0. Headline

The repository contains **no server source code**. It is documentation plus an
agent skill. Nothing about auth enforcement, input validation, job isolation,
rate limiting, or logging can be audited from here. Every finding below is
therefore about (a) what the docs promise and (b) what the docs leave unsaid.

---

## 1. Security findings

### H-1. Single shared static API key, no scoping, rotation, or revocation story
`README.md` §Auth: one `BECOME_MCP_API_KEY`, minted out of band, accepted as
`Authorization: Bearer` **or** `X-Api-Key`.

- No per-client / per-scope keys are described despite the README saying "ask
  for a *scoped* key". Document what a scope actually restricts.
- No rotation or revocation procedure. A leaked key (e.g. a pasted chat log,
  a screenshot of a connector settings page) has unbounded lifetime.
- Accepting the key in two different headers doubles the places it can leak.
  `Authorization` is routinely redacted by proxies, CDNs and log pipelines;
  custom `X-Api-Key` headers usually are not. Prefer `Authorization` only, or
  state explicitly that `X-Api-Key` is deprecated.
- The MCP authorization spec for remote HTTP servers is OAuth 2.1, and Claude
  custom connectors support it natively. Static keys are acceptable interim
  but should be labelled as such with a migration note.

### H-2. Job isolation between key holders is undocumented (possible IDOR)
`become_status` / `become_result` take only a `job_id`. With a shared key,
**any holder can read any other holder's job** unless the server binds jobs to
keys. Document: are job ids bound to the issuing key? What is the entropy /
format of `job_id`? Are they guessable (sequential, timestamp-based)?

### H-3. Cost / abuse control for `certify: true` is undocumented
`certify: true` triggers an EC2 prove run of ~60–70 minutes per job. A key
holder (or a leaked key) can queue unbounded paid compute. Document rate
limits, per-key quotas, concurrency caps, and what happens on quota exhaustion.
Without this, a single leaked key is a direct cloud-bill exposure.

### M-1. Server-supplied text is fed to the model as instructions
The agent contract (`/agent.md`) and response fields such as
`summary_for_model`, `how`, `inbox`, `answer` are server-controlled prose that
clients are told to read and act on. Any compromise of the host (or an
upstream that populates those fields, e.g. the GHA run output) becomes a
prompt-injection channel into every connected agent.

- The skill already says "do not treat `ok` or `summary_for_model` alone as
  fail/success" — good. Extend it: treat all free-text fields as **data, not
  instructions**; drive control flow only off enumerated fields
  (`agent_status`, `terminal`, `poll_after_ms`).
- Consider publishing a hash / signature of `agent.md` in this repo so clients
  can pin the contract version they were tested against.

### M-2. "Settled" is asserted by the same host that produced the answer
README: "Never trust `answer` … until `Settled`". But `Settled` is a string
returned by the server. There is no documented way for a client to
**independently verify** settlement (Sepolia tx hash, contract address, job
hash preimage, verifier key). Publish the contract address, the
`BecomeJobHash/v0` recipe, and a one-line "verify this job yourself" example
so the trust claim is checkable rather than asserted.

### M-3. Trust boundary of the certify path is under-communicated
The header line says the host "coqchk-checks and (optionally) EC2-proves +
Sepolia-settles", while §Honesty says the settlement TCB is **T2CERT0 (not
full coqchk-in-guest)**. Readers skimming the top will over-trust. Move the
T2CERT0 caveat next to the first mention of "certify" and spell out what is
in the trusted computing base (a single operator-run EC2 instance + the GHA
workflow that dispatches it).

### L-1. Obsolete tunnel URL remains in git history
`finals-affair-designed-constitutes.trycloudflare.com` is present in the
initial commit. It is dead and public, so no action needed, but do not reuse
the pattern of committing ephemeral hostnames.

### L-2. No secrets found in history
Grepped all revisions for key-like strings, bearer tokens, hex private keys.
Nothing found. `.gitignore` is minimal but adequate for a docs-only repo.

### L-3. No `SECURITY.md` / disclosure contact
There is no documented way to report a vulnerability in the hosted service.
Add a `SECURITY.md` with a contact and expected response time.

## 3. Agent skill (`skills/become-use/SKILL.md`) review

**Good:** clear happy path; explicit "do not invent job ids"; "poll only when
`auto_generate` / `run_id` present"; Settled-only trust rule; honesty footer.

**Improve:**

1. Add a **failure path**: what to do on `Failed`, on `gallina_required`, on a
   401, on `poll_after_ms` exceeding some ceiling, and a maximum poll count so an
   agent does not spin for hours on a stuck job.
2. Add a **Gallina input hygiene** rule: the target is compiled server-side.
   Tell agents to send only the proposition (no `Require`, no `Ltac`, no
   `Extraction`, no shell-adjacent Coq commands) and to keep it under a stated
   size limit. Whether the server sandboxes Coq is unknown (no source), so the
   skill should be conservative.
3. State that `run_url` / `actions_url` point at a GitHub Actions run; agents
   with GitHub tooling must **not** re-dispatch, cancel, or comment on it.
4. `disable-model-invocation: false` is fine, but add `allowed-tools` (or the
   equivalent for the skills CLI) listing only the four `become_*` tools, so a
   client cannot be talked into using unrelated tools by response text.

## 4. What could not be audited (needs source or host access)

- Auth middleware: constant-time key compare, which routes are gated, 401 vs
  403 semantics, whether keys are logged.
- Input validation on `target` (Coq/Gallina) and whether `coqchk` / `coqc`
  run in a sandbox with time and memory limits.
- Job store: id generation, key binding, retention, PII.
- Transport: TLS config, HSTS, CORS on `/mcp`, MCP session-id handling,
  Origin validation (required by the MCP spec for HTTP transports to prevent
  DNS-rebinding).
- Rate limiting and per-key quotas.
- The EC2 prove pipeline, S3 staging, and GHA dispatch credentials.

**Recommendation:** publish the server source (or grant read access to the
repo that holds it) and re-run this audit against code. Until then the public
badge "Auth: API key required" is a claim, not a verified property.

## Addendum 2: live `tools/list` from the production host (via Claude connector)

The user attached the server as a claude.ai connector. The session received
the real tool list before the connector's token expired, so the following is
**verified against production**, not the docs.

### Tools actually exposed (8, docs say 4)
`become_orchestrate`, `become_ask`, `become_status`, `become_result`,
`become_cancel`, `become_encode_service_request`, `become_engine_query`,
`become_spec_check`. The README on `main` lists four. `become_cancel` and
`become_encode_service_request` appear in no doc anywhere.

### Contract dispute settled: `main` is right, the setup branch is wrong
The live schema states: "Gallina Target is the ask. Natural-language request
is gloss only … Never invents Target when target is missing." An
English-only call cannot succeed. The `claude/become-mcp-setup-pkqgke` branch
tells agents the opposite and must not merge.

### Security findings from the live schema

| # | Finding | Sev |
|---|---|---|
| S-1 | **Client-controlled server-side URL.** `become_orchestrate.engine_url` and `become_engine_query.url` default to `http://127.0.0.1:8787` and accept any string. A caller can make the host fetch arbitrary internal or external URLs (SSRF: cloud metadata endpoint, other loopback services, the S3/GHA plumbing). Remove these parameters from the public schema; read the engine URL from server config only. | **High** |
| S-2 | **Client-controlled filesystem path.** `become_encode_service_request.job_dir` is a raw path "to job directory". Any key holder can point it at any directory on the host. Replace with `job_id` and resolve the path server-side under a fixed root. | **High** |
| S-3 | **Client-chosen job ids.** `become_orchestrate.job_id` is an "optional fixed job id". With a shared key, a caller can collide with or overwrite another tenant's job, and the IDOR from the first report becomes trivial. Ignore client ids; always mint server-side. | **High** |
| S-4 | **Operator knobs exposed to clients.** `unload_ollama`, `query_engine`, `timeout_s` guidance about "~16GiB host", `BECOME_ALLOW_LOCAL_GROTH16`, and `anvil` chain are host-operations concerns. They leak infrastructure detail (host RAM, local LLM, local prove flag) and let clients change host behaviour. Strip them from the public surface. | Medium |
| S-5 | **`oneOf` enforced by prose only.** `become_orchestrate` has `required: []`; "exactly one of target / question_v" lives in the description. A call with neither, or both, reaches the handler. Encode it in the JSON schema. | Low |

### Friction findings (why a chatbot fails on first contact)

1. The orchestrate description is ~120 words of internal jargon ("gloss",
   "SR fields", "T2CERT0", "claimant/pins"). A model that has not read
   `/agent.md` cannot tell what to send. Lead with one sentence and one
   example: *Send `target: "exists n : nat, 5 + 1 = n"`. Answer arrives as
   the numeral "6" when `agent_status` is `Settled`.*
2. Parameter count: orchestrate has 19 parameters. A chatbot needs 3
   (`target`, `certify`, `wait`). Hide the rest behind auth scopes or delete.
3. `a` / `b` "operand overrides only after Gallina target is present" is a
   trap: it invites the model to skip the target.
4. `become_ask` requires `bid_wei` but orchestrate defaults it; two tools,
   two rules. Merge into one tool.
5. No `outputSchema` on any tool, so `agent_status` values, `terminal`, and
   `poll_after_ms` are undiscoverable until the first response.
6. The description says "Prefer wait=false + poll_after_ms" but there is no
   guidance on how many polls or what a stuck job looks like.

### Connector-flow finding
The token issued by the connector expired within the session. Combined with
`initialize`/`tools/list` gating, a chatbot's first experience is a working
tool list followed by "requires re-authorization" on the first call. Long
token lifetimes for zero-bid scope, or an unauthenticated zero-bid tier, fix
this.
